WHY VOID EXISTS

Programming should feel
like making something.

Easy to use. Productive to work in. Fast where it matters. Fun to come back to.

VOID starts with a practical frustration: the idea you want to build can be simpler than the machinery you have to manage to build it.

A small tool should take a small amount of code. A larger application should still have clear types, predictable behavior and room to grow. Working on native software should leave more attention for the program itself.

The compiler and runtime should handle complexity so application developers do not have to.

WHAT VOID IS TRYING TO IMPROVE

Less friction between
an idea and a working program.

01 / EVERYDAY CODE

Keep simple things simple.

The friction: ceremony can make a small operation harder to read than the idea it expresses.

VOID uses indentation, compact declarations, inferred local types and direct construction. A function without a result omits the result annotation. Receiver methods name their receiver explicitly. One for keyword covers iteration, conditions and repetition. Named arguments, pure defaults and multiline calls let a call explain itself. Typed if-expressions choose a value directly; string interpolation accepts string expressions without hidden numeric conversions.

A small application can start with executable top-level statements or a zero-argument main, selected explicitly with --app. Recoverable collection lookups let missing data be ordinary control flow. The aim is a small, consistent set of rules that remains useful as the program grows. Powerful types and predictable behavior should still be there when you need them.

02 / NATIVE SOFTWARE

Bring readability to native execution.

The friction: a productive editing experience and control over native data should fit into the same workflow.

VOID brings readable source to a statically typed language built on LLVM. Exact-width numbers, value structs, managed objects, interfaces and generics give you ways to express the shape of your data and the behavior your code needs.

Performance work focuses on generated machine code, allocation behavior and collections measured with real applications. Native execution is a foundation to develop, not a substitute for measurement.

Explore types and data
03 / MEMORY & RESOURCES

Keep lifetime machinery out of ordinary code.

The friction: memory bookkeeping competes with the work your application is supposed to do.

Automatic memory management is central to VOID. Ordinary code should not need manual frees, raw pointer arithmetic, an unsafe escape hatch, placement decisions or collector scheduling.

Values and shared objects still have distinct, explainable behavior. External resources have a separate lifetime: with, defer and deinit make deterministic release explicit rather than leaving it to garbage collection.

Understand memory and identity
04 / EXISTING LIBRARIES

Make native integration feel like VOID.

The friction: using an existing library can expose foreign pointers, string formats and ownership rules throughout application code.

The direction is typed .void wrappers and trusted bindings that handle those boundaries. Application developers should work with language values and managed resource identities, rather than learn a second string type just to cross into C.

Implemented subset Trusted host-provided static bindings demonstrate scalar calls, owned UTF-8 transfers, resources and callbacks. General library loading and a public binding workflow are still ahead.

See the native integration boundary
05 / ITERATION

Protect the state you are working in.

The friction: restarting an interactive program can mean reconstructing a scene, replaying inputs or losing the state that revealed a problem.

VOID’s live-development goal is to apply compatible function-body changes while the program keeps running. An incompatible edit should lead to a deliberate decision, rather than a forced restart that discards your session.

Runtime support + future workflow Compatible function replacement exists in runtime integration. Automatic watching and save-triggered replacement remain planned. Changes to layouts, signatures or incompatible capture structures cannot be applied as simple body edits.

Explore the live-development direction
06 / FEEDBACK

Give answers in the language you wrote.

The friction: an error is harder to fix when it points at generated machinery instead of the source you recognize.

VOID’s diagnostic direction is source-first: .void locations, useful ranges and understandable messages. Ordinary errors should speak about your program rather than require you to decode LLVM IR, mangled names or linker details.

The editor is part of that goal. Completion, hover, parameter help and navigation should help you understand your code while you write it. A shared language service keeps editor feedback tied to compiler analysis, including nested module paths, authored documentation and references inside interpolated strings.

Explore tooling and diagnostics
07 / ROOM TO GROW

Let the program choose its purpose.

The friction: language choices can become tied to one engine, platform or kind of application.

VOID Language is independent of VOID Engine. Games are one use case alongside desktop applications, tools, systems software and everyday programs.

The portability goal is consistent behavior across Linux, Windows and macOS where dependencies support those platforms. The language should give projects a common foundation without pretending that platform-specific libraries disappear.

Explore the language foundation
08 / A COHERENT LANGUAGE

Make the pieces work together.

The friction: individually useful features can become a collection of overlapping rules and special cases.

KISS and DRY apply to the language’s construction as well as its surface. VOID favors one authoritative compiler model, shared native lowering and consistent rules for values, references, effects and diagnostics.

The goal is to earn each feature’s place. More syntax, another execution system or an extra spelling should solve a concrete problem before it becomes part of the language.

WHAT MAKES THE DIRECTION DISTINCT

A deliberate combination.
One development experience.

VOID’s identity comes from the way its choices support one another.

Readable, indentation-based code belongs alongside static types and LLVM native execution. Automatic memory management belongs alongside explicit value and reference behavior. Pattern matching, results, resource cleanup and async work should follow understandable rules.

The wider ambition connects that language to useful editor feedback and a live-development workflow that respects a running application. Some pieces already execute; others are still being built.

That combination is what VOID is pursuing. Familiar ideas are selected for how they serve the whole experience.

THE PROMISE TO WORK TOWARD

Ambition with
clear boundaries.

VOID is in development. The direction is broad; every capability still has to earn its implementation.

Working foundation

Typed source, LLVM JIT/AOT, managed and value data, collections, generics, interfaces, patterns, closures, events, structured async work and bounded workers have implemented contracts.

Still being built

Automatic save-driven reload, broader native-library integration, package management and the complete public developer experience remain future work. There are no public builds available yet.
