  build/llvm23-isolated-candidate-2026-11-07/ubuntu/

CRYPTOGRAPHIC BEHAVIOR AND NEGATIVE-COVERAGE LIMITS

All 87 target outcomes are retained individually in the results JSON files.
The existing-vector-results.json files retain every actual/expected hash and both
mismatches; qualification-summary.json distinguishes the 85 matches from those
upstream oracle bypasses. In particular, the existing stream, stream2, stream3,
stream4, box_easy2, box_seal, secretbox_easy and secretbox_easy2 vectors match on
both environments. stream2 retains its upstream 4 MiB Salsa20 stream and 4000-byte
in-place counter/XOR checks. stream retains the XSalsa20 and counter-boundary
vectors. Inputs, assertions and expected files are unmodified.

This supports the expected cryptographic behavior for the exercised existing
vectors. It does not constitute independent cryptographic review or exhaustive
proof of every backend, message length, CPU or platform.

The unchanged sodium_utils2.c and sodium_utils3.c have ASan conditionals that
avoid their intentional overflow/underflow paths, then invoke a handler that
calls _exit(0). The common buffered result comparison/finalization is bypassed:
  sodium_utils2: actual .res is empty; expected .exp is 46 bytes.
  sodium_utils3: actual .res is empty; expected .exp is 43 bytes.
Both still report PASS via exit 0. These target passes do not establish those
fault branches or normal-exit leak finalization. The source also emits upstream
ASan warning text; build diagnostics are retained. These limitations pre-exist
the candidate and were not expanded or hidden.

Supplemental probes against each isolated candidate library, under the SAME
fatal instrumentation/options and without editing either upstream test:
  valid guard: nonnull, mapped without read/write permission; zero-length clear
               succeeds and the allocation is freed; exit 0.
  overflow:    the upstream utils2-style out-of-range clear is rejected fatally.
  underflow:   the upstream utils3-style canary damage/free is rejected fatally.
  guard-read:  reading the fixture's protected guard is rejected fatally.
All six invalid-access subprocesses emit AddressSanitizer diagnostics and actually
exit 86. These are expected supplemental fatal controls, not upstream test failures
or extra upstream passes. They verify relevant protection mechanisms separately;
they do not retroactively turn the two utility tests into full oracle passes.

The initial supplemental probe expected ASan exit 87 and failed its own oracle
when the overflow correctly died with an ASan report but exit 86. That first
script, result and diagnostic remain under pikaos/negative-probe-attempt1/.
The corrected oracle accepts a fatal sanitizer status with an ASan diagnostic;
no instrumentation, sanitizer flag or provider behavior was changed. Distinct
ASan-versus-UBSan exit codes are not proven for this combined-runtime invocation.
Actual statuses, rather than configured-code assumptions, must drive diagnosis.

SOURCE PROVENANCE / RECIPE / CACHE REVIEW — NOT IMPLEMENTED

1. Preserve upstream identity and apply only in a disposable source copy.
   tools/verify_host_deps.py:source_tree currently verifies exact upstream files;
   patching the permanent source cache would invalidate that contract. The
   original archive/hash must remain the original source identity. A reviewed
   patch identity, order, upstream origin, three before/postimage hashes and an
   applied-tree digest must be recorded separately. The experiment provides
   those concrete records in source-provenance.json. Future builder integration
   must use the same base verification and fail on unexpected files, missing
   patches or differing postimages. Windows already builds a disposable sodium
   copy for version-header generation; Linux/macOS currently configure against
   the pristine source cache and would need the corresponding copy step.

2. Current receipts do NOT require this patch.
   Read-only verify_prefix checks accept all three existing Linux prefixes under
   today's unpatched policy; their receipts have no mandatory patch identity.
   This is recorded in existing-receipt-review.json, not treated as candidate
   acceptance. A promotion must make expected applied-source policy mandatory
   and reject old/unpatched receipts before compiler configuration. Merely adding
   optional JSON fields or checking old binary hashes is insufficient.
   Linux's legacy receipt does not require recipe_sha256. Native schema 2 requires
   an exact recipe inventory. Update the existing receipt/verifier scheme across
   platforms so the patch and relevant builder/verifier recipe hashes are bound
   and older receipts cannot silently pass. Do not call a patched binary pristine
   1.0.22 solely because its base version/archive fields still match.

3. Record actual build and profile identity.
   Keep the exact original pins, compiler/SDK identity, build profile, flags,
   native SDK/deployment/CRT settings, shared zlib identity and installed-file
   hashes. Add explicit applied-backport provenance through the current receipt
   system, not a second dependency manager. Rebuild/reverify affected prefixes;
   copying the experiment archive or hand-editing a receipt is not integration.
   No such change is made by this experiment.

4. Existing caches and compiler/native identities have different roles.
   tools/ci/voidup_bootstrap.py does not cache host prefixes and refuses implicit
   reuse during bootstrap. tools/install.py does reuse an existing host prefix
   when a receipt exists, so patch-aware verifier rejection is essential there.
   CMakeLists.txt already hashes host archives, their receipt and host recipes
   into compiler build identity; cmake/CacheBuildIdentity.cmake derives that
   identity from actual inputs. A rebuilt archive/receipt changes the existing
   compiler object-cache identity. Include the approved patch/policy files among
   those expected inputs too; do not rely only on a coincidental binary change.
   cmake/NativeBuild.cmake and NativeInventory.cmake already hash host link
   archives for build/install native-resource manifests and depend on the actual
   archives. Regenerate these through the normal build; preserve their checks.
   The LLVM SDK archive identity remains LLVM 23.1.4 and must not be changed to
   represent a sodium backport. HTTP's current cache recipe list includes shared
   files such as NativeBuild.cmake, so a later packaging edit there can cause an
   existing HTTP cache-key change. No HTTP transport/cache rewrite is needed.

5. Corresponding-source and notice packaging must describe the compiled source.
   NativeBuild.cmake currently installs the original sodium/libarchive archives
   and provider receipt. InstallLicenses.cmake installs host notices, pins and a
   fixed list of builder/verifier files. These rules do not automatically ship
   this candidate patch or a patch-policy manifest. A patched-provider package
   needs the unchanged base archive PLUS the exact approved patch, provenance,
   application order and complete build/verification inputs matching its receipt.
   Preserve upstream ISC terms/attribution; a copy is included here for review.
   Update the existing notice/source inventory and installation validation to
   account for the applied source, without relabeling original archive hashes.
   The native recipe imports tools/ci/llvm_sdk.py, which is not in the current
   host license-install file list. A reproducible source handoff must include
   required shared helpers in their expected layout or document an actual
   reproducible checkout, rather than presenting relocated scripts as standalone.
   The existing redistribution audit already records source/rebuild limitations;
   this experiment neither repairs nor clears them. No package was installed,
   assembled, published or declared redistributable.

Current policy files and hashes reviewed are recorded in reviewed-policy-inputs.json.
These findings are an integration review, not hidden recipe/pin modifications.
