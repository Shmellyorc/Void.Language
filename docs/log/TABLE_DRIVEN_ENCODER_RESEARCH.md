# Could a fixed UTF-8 encoder improve logger performance?

**HOLD implementation.** A fixed classifier can express every logger escape exactly. It could remove substantial rule preparation on escaped and long messages. The retained length-dispatch candidate already skips map construction on every message in file200, however. Its entire short-quoting benchmark takes **1.657 ms per 200 messages**, while full file200 takes **16.722 ms** against **<10 ms**. These are separate measurements. They make a new private compiler/Runtime operation a poor first choice for closing the file gate. If Wrench independently prioritizes heavy quoting, the smallest credible dedicated design is a scalar ASCII table with a Unicode range fallback. [Length-dispatch receipts](evidence/length-dispatch-20261105/results.json)

## Exact policy

I compared all 81 source key/replacement pairs with the existing independent byte oracle. All agree. There are 35 ASCII and 46 non-ASCII keys. The following rows partition them. [Logger policy and sizing](../../stdlib/log.void#L321) · [Independent oracle](../../tests/log/oracles.py#L10)

| Input scalar(s), hexadecimal | Count | Exact output |
| --- | ---: | --- |
| 0009, 000A, 000D, 0022, 005C | 5 | Two ASCII bytes each: backslash followed by lowercase t, n, r, double quote or backslash respectively |
| Remaining 0000–001F, plus 007F | 30 | Literal backslash, lowercase u, four zero-padded lowercase hex digits |
| 0080–009F, 061C, 200E–200F, 2028–202E, 2066–2069 | 46 | Same six-byte form |
| Every other valid scalar | — | Copy its original UTF-8 bytes |

Thus backspace and form feed use six bytes. Combining marks, emoji, U+200D, U+202F and U+206A pass through. Output is never rescanned. A 256-entry table can classify an unsigned input byte as ordinary ASCII, short escape, six-byte escape or non-ASCII. For non-ASCII, use the existing UTF-8 width/validity check and compare the decoded scalar with the five listed groups. Continuation bytes have no independent escape meaning. Preserve the invariant-failure channel for malformed managed UTF-8. [Current scalar walk](../../src/runtime/text_case.cpp#L120)

## Algorithm and ownership choices

| Choice | Short messages | Long or escape-heavy messages | Cost and disposition |
| --- | --- | --- | --- |
| Direct branches and ranges | No setup. A printable-ASCII check must still exclude quote, backslash and DEL. | More comparisons per scalar. | Portable scalar reference. No measured winner over a table. |
| ASCII table + Unicode ranges | One fixed lookup per ASCII byte, no per-record rule validation. | Copy ordinary spans in bulk and expand matches. Long changed messages still need exact sizing and assembly. | Preferred dedicated design. Small read-only data, portable unsigned indexing, no persistent application state. |
| Byte-driven UTF-8 state machine | More state for ordinary input. | Could recognize multibyte escapes directly, but would also need to distinguish invalid UTF-8 and preserve pass-through spans. | Duplicates work already done by the scalar validator. HOLD. |
| Word-at-a-time or SIMD scan | Setup, tail handling and dispatch compete with useful work on 64-byte inputs. | Could skip long ordinary spans; dense escapes shorten those spans. | Requires bounds-safe loads, scalar tails and portable fallback. No evidence that ASCII detection dominates. HOLD. |
| Existing generic length dispatch | For eligible inputs up to 128 bytes, the helper proves disjointness, validates all replacement references and returns the input alias. | Long inputs bypass the helper. Escaped or inconclusive inputs use the leased general rule path. | Already measured and present uncommitted. The source hash matches the receipt. Retain it for its separate review. [Source](../../src/runtime/text_case.cpp#L144) · [Earlier rejected variant](HEAVY_PATH_INVESTIGATION.md) |

**A. Ordinary VOID.** The logger already counts escaped bytes in source during configuration. A source encoder can use checked UTF-8 arrays, count first, allocate within budget, fill the array and use checked string construction. Managed ownership follows existing language rules. It must avoid repeated string concatenation and preserve the unchanged-input alias. For a performance decision the adverse evidence is concrete: a checked VOID loop over *already prepared bytes* took 20.609 ms per 200 in one short-input component test, versus 4.708 ms for quoting. This was a different loop, not a timing of a source encoder. Converting each input to a managed array would add work. HOLD this option. [Component definitions](../../tests/log/performance_framing.void) · [Measurements](evidence/llvm23-framing-20261104/results.json)

**B. Dedicated Runtime encoder.** If later authorized, restrict the private call to the canonical logger module, following existing frontend, IR provenance, JIT binding and linked AOT patterns. The operation would take the registered immutable input and remaining byte budget. It would have no caller-supplied rule arrays. Share one classifier between count-only configuration validation and quoting. Keep framing, admission, errors and sinks in VOID. Moving fixed policy from source into the shipped Runtime is a real ownership and ABI decision for Wrench and Boss. Public logger and text signatures need no change. A policy or global-layout change must participate in compiler/runtime cache compatibility and require restart where reload rejects a changed schema. No live pointer, plan, rule lease or managed reference should persist between calls or applications. [Current private-operation contract](BOUNDED_FRAMING_RESULT.md#implementation-and-safety) · [Reload contract](../RUNTIME_GLOBALS.md#reload-cache-and-tooling)

**Failure and publication.** Preserve the logger's budget-before-empty check, raw frame limits, name-before-message order and distinct remaining budgets. Configuration maps an oversized escaped name to invalid configuration; writing maps overflow to the existing frame error. Keep timestamp sampling, exact separators, final LF and sink ordering. At the ABI boundary validate registered output/input before shortcuts. A bounded short proof may inspect a managed string only inside checked access. For longer input use the existing chunked owned snapshot, reacquiring after polls at the 16 KiB quota. Count with checked remaining capacity, then assemble only changed output from spans under NativeSafe. Publish an unchanged alias under the lock after revalidation, or use checked immutable-string publication after successful assembly. Leave aliased outputs untouched on error. Preserve allocation/invariant failures and cleanup. Removing allocations changes fault-injection ordinals. The existing full-input reserve and final publication still have pause-time limitations. [Framing and validation](../../stdlib/log.void#L376) · [Runtime publication](../../src/runtime/text_case.cpp#L279) · [Root and failure tests](../../tests/text_encoding/ownership.cpp#L51)

The general text operation must keep validating dynamically supplied arrays, even on empty input, with its existing lease, invalid-rule and budget error ordering. Private logger globals happen to contain the fixed policy today. Recognizing their addresses, lengths or current values as proof of future immutability would be unsafe. If changing policy ownership is unacceptable, retain generic dispatch. [Public text contract](../../stdlib/text.void#L564) · [Prior reuse analysis](ESCAPE_RULE_REUSE_RESEARCH.md)

## How much work could disappear?

- **Before length dispatch**, one instrumented file200 sample spent 5.944 ms in translation, including 4.411 ms preparing rules and 0.748 ms disposing of them. The input lookup/size pass was 0.121 ms. All 200 outputs aliased the input. A fixed scanner removes map construction, replacement snapshots and disposal wherever the general path still executes. Faster lookup alone targets little of that original short workload. [Attribution](SMALL_FILE_INVESTIGATION.md#translation-follow-up--golden-wrench-review-pending)
- **Against the current candidate**, file200 already avoids those map costs. The remaining short opportunity is chiefly 81 replacement checks and lease setup per nonempty quote. Even eliminating the entire separately timed 1.657 ms quote component is an optimistic scale reference, not a full-file forecast. Actual input classification and checked publication remain. The current heavy medians are 5.440 ms for quote100, 7.993 ms for frame100 and 18.339 ms for console100. Only part of heavy quote100 can disappear. Expansion, immutable string publication, frame construction and console delivery still execute. There is no measured incremental speedup for the proposed encoder. [Matched comparison](evidence/length-dispatch-20261105/results.json)
- File acquisition, 200 writes delivering 15,000 bytes, final durable flush and close remain in file200. An earlier separate observation recorded 5.481 ms in native flush alone. Prepared direct-file controls also vary between blocks. Neither number is a universal floor or a term to add to separately timed quoting. [Small-file investigation](SMALL_FILE_INVESTIGATION.md)

**Review decision.** Keep LOG-PERF open. Before commissioning a dedicated encoder for file200, require evidence that the remaining fixed-rule checks in the retained candidate materially affect whole-file CPU. If a heavy-workload experiment is separately approved, compare directly against length dispatch using matched blocks. Require exact oracle bytes for all keys and adjacent unescaped scalars, exact and one-byte-short budgets, repeated and distinct messages, unchanged aliases, moving/forced GC, failed allocation and aliased output, normal/O2 JIT and independently linked AOT. Retain the hard 1 MiB stack, full write/rotation/fsync/close checks and incident records. Stop for any byte/error difference, unsafe lifetime, consistent heavy regression, or failed heavy screen (frame ≤10 ms, console ≤20 ms). A partial gain leaves file200 failed until the original <10 ms gate passes.
