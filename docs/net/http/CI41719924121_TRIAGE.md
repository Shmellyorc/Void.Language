## Confirmed defect and controlled reproduction

`prerequisite_callback` directly re-queries Schannel's
`SECPKG_ATTR_APPLICATION_PROTOCOL` on **every** required-h2 request. It previously
required a fresh `Success`/`h2` result each time. Schannel can instead return a
successful query with `None` and an empty protocol after a handshake update.
This does not revoke the established connection's ALPN. The pinned curl
`schannel_connect_step3` explicitly preserves its negotiated ALPN in that case
while `recv_renegotiating` is true, and rejects an explicit protocol change.
See [upstream investigation](https://github.com/curl/curl/issues/9451) and the
retained `third_party/curl/lib/vtls/schannel.c` implementation, around
`SECPKG_ATTR_APPLICATION_PROTOCOL`. No vendored source change is required.

The inconsistent guard is a confirmed production availability defect. A native
test hook models **only removal** of Schannel's later ALPN observation; it never
creates an h2 result or changes wire negotiation, TLS validation or curl's
connection. With diagnostics but the original guard, the controlled native
Debug run fails at:

| Observation | Controlled before-fix result |
| --- | --- |
| Request | GET `/alpn-missing`, warmup iteration **0** |
| Previous request | `/alpn-observed`, real h2, successful complete body |
| Connection | Same client and curl connection ID **0** |
| Effective ALPN observation | query succeeds, status `None`, length 0 |
| Public error | `unsupported` (5), `tls` (5), domain `none`, native code 0 |
| Curl completion | **42**, pre-request callback abort |
| Response/progress | no metadata, status 0, uploaded/encoded/decoded/buffered 0 |
| Remote outcome | known not sent (`remote_outcome_unknown=false`) |
| Peer | sees initial stream 1; sees **no** `/alpn-missing` request |

The old guard's explicit Error preserves native code 0; the separate provider
diagnostic carries curl 42. Both are retained, without relabeling one as the other.
The before-fix source hashes and complete failure/peer receipts are retained.

On this Windows 10 Home VM (build 19045), the **unchanged** Debug and Release tests
both pass. New peer receipts show TLS 1.2. Schannel TLS 1.3 is supported starting
with [Windows 11 / Server 2022](https://learn.microsoft.com/en-us/windows/win32/secauthn/protocols-in-tls-ssl--schannel-ssp-).
TLS 1.3 post-handshake processing is therefore a plausible explanation of the
platform difference, consistent with upstream behavior. **The original CI did
not record TLS version or the failing ALPN result. That attribution is an
inference, not a native Server 2022 reproduction.** The next instrumented hosted
run must confirm or disprove it; another cause must be investigated if its
receipts disagree.

## Production correction and ownership

Windows ClientState retains a successfully observed native `h2` ALPN proof for
the **exact curl connection ID and active socket**. Only a successful query
reporting `None`/empty may use that existing proof. A missing TLS pointer, failed
query, explicit non-h2 result, new connection or different client cannot create
or borrow proof. An explicit incompatible result clears the previous proof.
Ordinary negotiated h2 also records proof before a later required-h2 request.

The four fixed entries match the existing validated maximum of four connections
per client. `CURLOPT_CLOSESOCKETFUNCTION` erases proof before calling the same
Windows `closesocket`; there is no time-based history or unbounded cache.
The callback data points to ClientState, which owns its multi and survives its
cleanup, rather than to an easy handle/TransferState. Curl documents both
[connection ID scope](https://curl.se/libcurl/c/CURLINFO_CONN_ID.html) and
[close callback lifetime](https://curl.se/libcurl/c/CURLOPT_CLOSESOCKETFUNCTION.html).
All accesses and close callbacks run on the existing driver thread.

This preserves reuse and multiplexing. It neither forces fresh connections nor
retries unsuccessful requests. The earlier `request_permitted` replay guard is
unchanged and still runs **before** retained ALPN can permit a request.
No certificate, key, TLS version/cipher, verification, proxy, cookie, DNS, session
ownership, cancellation, Runtime, GC or public API policy is relaxed. The added
proof storage and socket callback are Windows-only; the OpenSSL ALPN check and
Linux/macOS connection handling remain unchanged.

## Diagnostics and regression controls

Test-only hooks record target, curl connection ID, guard decision, request-byte
count, TLS getinfo result and raw Schannel ALPN query/status/length. Receipts
explicitly mark injected omission. Ordinary Driver users have neither hook.
The latency helper now records the exact failing profile, zero-based iteration,
target, error/phase/domain/code, response and progress before failing. It still
runs **8 warmups and 64 measured requests** with the same buffer limits, clock,
sorting and CPU accounting. Every successful h2 latency response must additionally
have actual h2 metadata and the expected body.

The existing H2 peer records TLS version, ALPN, request/stream IDs, paths/methods
and end/body counts. It asserts the original h2 latency workload uses stream IDs
1 through 145, odd numbers, on one connection: initial request plus all 8+64.
No latency timing, sleep, retry, flow-control, frame, body or response is relaxed.
The additional Windows GOAWAY teardown correction is described below.

The Windows omission controls require:

- 8+64 real h2 requests succeed on the originally authenticated connection after
  the observation is suppressed; bodies and protocol remain genuine.
- A fresh owner with missing proof fails before headers/body/origin bytes, even
  when its numeric curl connection ID is reused.
- Six GOAWAY/replacement cycles exceed the four-entry storage bound. Each new
  connection first fails without proof, then establishes its own proof and reuses
  it successfully. Closed sockets cannot exhaust or authenticate the cache.
- A normally negotiated connection can later satisfy required h2 using its own
  proof. Peer counts require exactly 79 accepted missing-observation requests;
  the seven fresh missing-proof requests must be absent, with no stream 1 accepted
  on that path.
- The existing non-h2 origin and double-TLS proxy controls still fail before
  incompatible origin bytes. REFUSED_STREAM still records exactly one mutating
  request/body and rejects automatic replay. GOAWAY, reset prefix, header budget,
  paused DATA/window bounds, simultaneous streams, duplex, cancel and close
  checks remain in the native test.

Store RSA/ECDSA, explicit selection, anonymous/invalid identity negatives, P12
rejection, exact peer certificate checks, source JIT/AOT, forced GC, active
Runtime shutdown, timeouts, poisoned proxy environment and existing strict
policy assertions remain enabled.

## Independently exposed Windows GOAWAY fixture defect

The first broader Debug run reached the new churn control, then failed on its
first `/goaway`. The peer had received stream 147; the replay guard correctly
rejected curl's second pre-request attempt. This is **after** warmup and is not
the original CI failure.

An isolated buffered-trace stress reproduced it on the **54th GOAWAY**, curl
connection 53: `Recv failure: Connection was reset`, Schannel receive error 56,
`Failed receiving HTTP2 data: 56`, then `Connection died, retrying a fresh
connect`. The second attempt is aborted by the unchanged replay guard. A prior
64-cycle run with immediate diagnostic printing did not reproduce it; the
in-memory trace removed that logging timing effect. These diagnostic builds and
failures are preserved separately and are not acceptance passes.

The peer sent final response DATA and GOAWAY, then immediately closed its TLS/TCP
socket. Closing Winsock with unread client control bytes can reset the connection
and discard the final response. The Windows fixture now reads those in-flight
bytes until curl retires the connection after reading GOAWAY/END_STREAM. It uses
the existing ten-second safety guard and fails the peer assertion on timeout or
reset; it adds no sleep, retry or larger deadline. The final six-cycle Debug
receipt records **39 trailing bytes on each of seven GOAWAY connections**, all
ending with peer EOF. Thus the formerly unread bytes are directly observed.
After correction, a separate **512-cycle** native/peer stress passes: all 513
GOAWAY connections drain to EOF, with exact peer counts increased to match the
larger diagnostic workload. Its original 8+64 latency measurements are unchanged.
The ordinary six-cycle source and Debug executable were then restored exactly.

This restores the existing **graceful** GOAWAY test purpose: same response, last
accepted stream ID, error code 0, complete body, retirement and subsequent new
connection. New streams are not accepted after GOAWAY. Linux/macOS keep their
original teardown branch. Temporary curl verbose tracing was removed; final
diagnostics use only the narrow prerequisite receipt.

### Optimizer isolation

The preserved debugger stacks identify the O2 loop pipeline before example
invocation. To test whether the repair changed the generated IR, two isolated
hosts printed the module immediately before the original pass pipeline. They
used the same diagnostic backend object and different HTTP runtime archives.
Both emitted the same 15,408,393 bytes (`fd3c96adbd38402de317af185723765407fe4a63152e87b1995576fc2f787680`).
Both continued through O2. Their final exit 1 is the example's missing-URL
exit. These capture runs exercise compilation, not example acceptance.

Pinned `opt.exe` accepted the captured module with the verifier, default O2
and O2 with per-pass verification. A second executable linked LLVM without
VOID or curl, parsed the same module, ran the host's pass-manager registration
and default O2 pipeline, and verified the result. It completed both with the
ordinary allocation layout and with 1,024 retained allocations before parsing.
The baseline-runtime JIT comparison also completed both allocation cases in a
single compile-only host build. These results establish that the textual IR
alone is insufficient to reproduce the observed access violation in these
configurations. They do not establish the validity of every live analysis
object in the failing process, or distinguish a lifetime problem from an
optimizer or link-sensitive defect.

A second capture used `module.print(dump, nullptr, true)` to preserve LLVM
use-list order. Both runtime links again emitted identical input, now
15,675,838 bytes (`580575ef2aa7ffa6654f55bb5c858829a7fc2d9099a1925bb13325fec57dde5f`).
Both the SDK optimizer and the isolated host-equivalent O2 pipeline completed
on that input. The earlier baseline/candidate crash-rate difference still
stands. These experiments do not classify it as pre-existing or caused by
the HTTP repair.
