## Shared connection-wait failure: cancellation and resumed producer

The three failed cancellation runs have the same important evidence: stdout
reports `timeout`, phase `connect`, native code 28; stderr is empty; the peer sees
`/slow`, but never `/plain`, then sees the held connection close about ten seconds
later. Execution returns through the barrier's HTTP error before `pending.cancel()`.
The held body never completes normally. There is no observed loss of a Runtime
cancellation diagnostic or premature successful completion in these failures.

VOID unconditionally enabled `CURLOPT_PIPEWAIT`. In the pinned curl, a second
transfer may enter `MSTATE_PENDING` while the first connection is resolving or
connecting. `url_match_fully_connected()` / connection matching records the
pending candidate. `multistate_connecting()` schedules pending transfers on a
new *multiplexed* connection, but not on a new HTTP/1.1 connection. An ordinary
HTTP/1.1 response does not trigger the upgrade-completion notification either.
The pending transfer can remain stuck until the busy first connection finishes,
even when the multi's connection limit permits another connection. A held body
makes this circular wait visible.

This mechanism was reproduced locally against both the actual pinned curl and
VOID's actual Driver, using a controlled loopback DNS delay. The prior policy
produces curl's `Waiting on connection to negotiate possible multiplexing`, then
`PENDING handle timeout`; the first held response is still incomplete. The
explicit HTTP/1 control succeeds. The corrected negotiated case succeeds and
closes the held connection through cancellation before fixture teardown.

The macOS Debug producer failure has another circular dependency: it sends the
first 1 KiB, then waits for a same-origin `/producer-seen` request before supplying
the second block. If the barrier enters that pending state, the upload's **total**
deadline can expire while its producer is idle. Only detachment then releases the
barrier. The following write fails immediately with `timeout/upload`, 1,024 bytes
uploaded, and unknown remote outcome. That error phase does not identify which
clock expired. The original fixture timed only the final write, not the barrier.

A paired Driver control changes **only** the PIPEWAIT policy between two linked
variants. Both retain a 20 ms write deadline and a 60 ms producer pause:

- Prior policy: peer reads 1,024 bytes; the 2 s total deadline ends the upload;
  peer receives `/plain` only afterward; result is timeout/upload, uploaded=1024,
  whole-operation elapsed 2062 ms.
- Corrected policy: the barrier arrives before total expiry; peer receives both
  blocks; success with uploaded=2048, whole-operation elapsed 212 ms.

[Paired receipts and reproduction sources](evidence/ci41443618378/controls/).
The test's total deadline is deliberately shorter than the original 3 s deadline
and its barrier retains the ordinary 10 s connect deadline. This reproduces the
failure without increasing any limit. The exact Darwin scheduling/clock choice
was not logged originally; its attribution follows source analysis and this
controlled reproduction, not a claim of a local macOS execution. New
`producer-barrier` timing in the original timeout probe makes the next hosted
observation distinguish a blocked barrier from genuine write-idle failure.

**Production correction:** enable PIPEWAIT only for `http2_required`. Negotiated
requests can establish another connection within the existing multi limits;
they still reuse and multiplex established HTTP/2 connections. Required HTTP/2
retains its speculative multiplexing wait. No new scheduler, retry, vendor patch,
connection-budget increase, deadline change or cancellation implementation was
introduced. Initial negotiated HTTP/2 requests may establish more than one
connection, bounded by the unchanged total/per-origin limits.

The permanent `http_dns` regression covers negotiated held response, explicit
HTTP/1 control and paused producer with delayed local DNS. It checks independent
barrier completion, an unfinished held task before cancellation, actual peer
connection close before teardown, both uploaded blocks, and successful cleanup.
The DNS delay creates the failing schedule; it is not a production sleep or a
retry used to hide failure. Existing example positive cancellation and separate
header-timeout negative control remain intact.

## Windows explicit trust: three tests fail before authentication/TLS

These failures were inspected independently:

- `http_native`, **both** profiles: first failing assertion is `owned trust
  survives caller file mutation`, kind 23 / native code 4. Earlier ordinary HTTP,
  streaming and bulk cases passed.
- `http_timeouts`: `digest-upload` is `other`, kind 23 / native code 4, uploaded=0,
  elapsed=1 ms. The fixture never signals its authenticated-body event. This is
  not an expired Digest upload deadline or a mismatched expected success value.
- `http_examples`: `authenticated_post.void` exits 1, with empty stderr and stdout
  reporting HTTP `transport_failure`, phase `download`. The program prints its
  returned HTTP error normally; there is no missing stderr propagation.

All three explicitly configure a CA snapshot. `configure()` called
`CURLOPT_CAINFO_BLOB`, cleared CAINFO, then set `CURLOPT_CAPATH` to null. curl's
`setopt.c` checks `SSLSUPP_CA_PATH` even for a null CAPATH. Its Schannel backend
advertises CAINFO_BLOB but **not** CA_PATH, so it returns `CURLE_NOT_BUILT_IN` (4).
VOID throws from that checked setopt and detaches before the HTTP/TLS exchange.
The generic classifier's `download` phase was misleading here. Proxy CAPATH would
fail for the same reason after the origin option was corrected.

**Production correction:** omit both unsupported directory-clearing options on
the pinned Windows Schannel profile. Preserve the owned origin/proxy CA blobs,
null CAINFO paths, peer/hostname verification, TLS minimum and explicit-trust
SSL options. AWS-LC profiles still clear their compiled-in CA directories, which
is necessary for replacement trust. No failure is ignored and no system-root or
ambient libcurl fallback is added. The existing native snapshot, wrong-root,
hostname, TLS/auth/proxy and identity checks remain required on Windows; their
corrected native result is **UNVERIFIED**.

importing dependencies that deliberately reject multi-configuration generators.
The c-ares import test now explicitly selects Ninja on Windows and Unix Makefiles
on Unix. The negative missing-archive/digest check remains. Production CMake's

nine other fixture configurations because this local host has no Ninja executable;
that log is retained, not counted as a passing control. The scoped c-ares control
and normal whole-suite runs are the relevant verification.

`url_source` used `native_text()` and expected CRLF on Windows. The established
[console contract](../../stage10/CONSOLE_IO.md) specifies exact UTF-8/LF source
print records even under Windows redirection; CRT newlines apply only to CLI-owned
legacy trailers. Captured output is exactly seventeen `true\n` records. The fixture
now expects those exact bytes in JIT/O2 and independently linked AOT. No captured
output is normalized and no production Unicode or text path changes.

Example assertion failures now include actual exit status, stdout and stderr,
in addition to the existing saved command/output files. A returned HTTP error
will no longer appear in the immediate assertion as an unexplained empty stderr.
