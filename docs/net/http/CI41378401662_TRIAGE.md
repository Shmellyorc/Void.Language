## Windows: compile the source objects with the static ABI

In curl 8.23.0, Windows defaults `SHARE_LIB_OBJECT=ON`. Sources are compiled into
`libcurl_object`; `libcurl_static` consumes those objects. PRIVATE definitions
on the archive cannot propagate backwards into a separately compiled target.

The original Ninja rules for `psl.c.obj`, `cookie.c.obj` and `version.c.obj`
contain **no `PSL_STATIC`**. Only the separately compiled VOID keylog stub on
`libcurl_static` has that definition. Upstream CFLAGS already supply
`CARES_STATICLIB` and `NGHTTP2_STATICLIB`, explaining why those imports did not
fail alongside PSL. LLD explicitly reports the direct `psl_*` symbols available
in the verified `psl.lib`, but incompatible with `__declspec(dllimport)` callers.
This is not a missing library, dependency pin or CRT failure.

`CurlProviderObjects.cmake` now selects the actual compilation target:
`libcurl_object` when present, otherwise `libcurl_static`. Static dependency
macros and Windows platform macros apply there. Existing public Windows usage
requirements remain on the archive. The same target selection also corrects
source ownership of the disabled-keylog replacement, Apple visibility and
sanitizer instrumentation. Otherwise those policies would still miss the
object-library build. Sanitizer link requirements continue to propagate from
the archive to consumers.

The new `http_curl_objects` regression configures both CMake target layouts,
checks their generated compile commands, then compiles actual x64 COFF probes
with the pinned Clang and verified libpsl public header. All six references are
direct static references with the policy; removing **only `PSL_STATIC`** produces
six `__imp_psl_*` references. This is a COFF/compiler simulation, not execution
of Windows binaries or a replacement for native linking.

An additional real Linux curl build with `SHARE_LIB_OBJECT=ON` compiled **195
objects with ASan+UBSan**, built the archive and verified exactly one definition
of each of the six disabled-keylog functions. The upstream keylog source is
absent from its compile commands. [Actual object-library build receipt](evidence/ci41378401662/shared-object-build.json).

No vendored curl/libpsl source, static CRT setting, source checksum, dependency
pin or library functionality was changed. The new helper is included in the
existing HTTP CI cache identity, so a reviewed first hosted use gets a new
verified cache identity rather than reusing an obsolete policy seal.

## Producer deadlines: current provider state, not cached notifications

The failing peer assertion is its **second** 1 KiB read. Its first read completed
and signalled `/producer-seen`. Thus the first block reached the peer; the
transfer failed before delivering the second block. The earlier fix recognized
an idle fixed-length producer only when VOID's cached upload count equalled its
admitted count. That cache was updated by XFERINFO callbacks, not every send.

The pinned source can send the initial body in its HTTP DO phase. The subsequent
speed check can enter `MSTATE_RATELIMITING`, which removes socket interest until
its timer permits more work. There need not be a progress notification between
that send and VOID's 20 ms deadline. `CURLINFO_SIZE_UPLOAD_T` reads the current
provider counter directly, whereas a saved XFERINFO argument can still be zero.
Darwin's callback scheduling is not interchangeable with the earlier Linux
probe's schedule. Original hosted logs contain no callback/queue trace, so the
exact Darwin callback sequence is not claimed as directly observed.

The owning driver now samples `CURLINFO_SIZE_UPLOAD_T` before evaluating phase
deadlines, through the same overflow-checked upload/protocol-transition helper
used by the callback. The existing fixed-length/queue-empty/unfinished producer
predicate then sees current state. Unknown-length chunk framing and multipart
are still excluded from raw-byte equality. Unsatisfied producer writes and
provider-buffered bytes still keep write deadlines active. No curl source change,
second driver, timeout increase or synthetic success is introduced.

The regression retains the ordinary and original rate-limited cases. A third
case uses curl's actual `CURLOPT_NOPROGRESS=1` via native fixture authority,
forcing the notification-independent path. With the new service-time refresh
removed, this produces the exact error signature and reports **1,024 bytes
uploaded at detach**: timeout/upload, unknown remote outcome, immediate failed
resume. [Negative control](evidence/ci41378401662/local-deferred.stdout).
With the refresh present, all 2,048 bytes succeed. The silent-callback case also
requires a real blocked write to time out and a producer-idle total deadline to
expire around its explicitly shorter 200 ms budget, after the first block is
sent. The original 20 ms write deadline and 3,000 ms resume-case total deadline
are unchanged. TLS/proxy timeout phases, Digest replay and file-drain checks
remain in the same test.

## Cancellation: establish readiness and observe close

The source returns `Err` through `?` when its barrier HTTP request fails, before
executing `pending.cancel()`. The entry then prints the HTTP error and returns 1
normally. That exactly explains Debug's stdout/exit/stderr combination. It does
not establish a scheduler cancellation-propagation defect. The original log
omits the HTTP phase/native code and peer timing; the precise native cause of
that control-request timeout cannot be recovered from those artifacts.

The previous fixture's six-second sleep was a timing assumption, not proof that
the pending request had started. Cancellation now uses a fresh loopback peer and
an explicit readiness handshake: `/plain` returns only after `/slow` is active.
The held response never completes automatically. The test observes EOF/reset on
that connection **before fixture teardown**, as well as requiring the original
`Async task cancelled` diagnostic and no stdout. This tests cancellation of an
actual native pending request and structured close, not merely exit code 1 or
cancelling a task before it starts. It retains the same client, scheduler,
Runtime and production timeout policies.

A separate negative-control copy of the example lowers **only its barrier
header deadline to 20 ms**, while the fixture delays that response by 60 ms.
It must produce an HTTP timeout in the headers phase and empty stderr, closing
the pending connection through normal owner cleanup. That confirms the
pre-cancellation error path is distinct from a cancelled task. The published
example now includes phase/native code in its existing HTTP-error diagnostic so
a future native failure cannot hide that distinction. No Runtime cancellation
code or expected cancellation diagnostic was weakened.

This fixture repair and both observed paths pass locally. Native macOS Debug
must still rerun the example; this report does not pretend the old native timing
failure was reproduced on Linux or certify an unobserved Darwin schedule.
