## Windows Release: normalize at the consuming CMake boundary

`setup_http_deps_native.py` passes native `Path` values as individual subprocess
arguments. The failure is CMake's later interpretation of the untyped
`PSL_SOURCE` value in source entries, including `D:\a\...\src/psl.c`; the
artifact reports `Invalid character escape '\a'` for both selected sources.

`cmake/http-psl/CMakeLists.txt` now applies `file(TO_CMAKE_PATH ...)` to
`PSL_SOURCE` and `PSL_DATA` before existence checks, generator invocation and
source registration. This normalizes the path at its consumer, including callers
other than the Python recipe. Python's argument-list execution, exact two-source
selection, source ownership and static MSVC CRT remain unchanged.

The added policy regression configures the actual libpsl CMake project with
native backslashes, spaces and an `a source` directory, and checks generated
output. Linux execution simulates the problematic separator input; it is not a
Windows compiler/CRT acceptance claim. The same regression is registered in the
existing native CI policy test.

## macOS: C-locale decimal conversion with the existing contract

Both native artifacts show `src/runtime/conversion.cpp:61` instantiating the
floating `std::from_chars` overload marked available only from macOS 26.0 in
Apple's libc++ headers. The successful preceding configure stages confirm the
HTTP feature check was no longer the blocker.

The Apple-only floating branch now uses `strtof_l` for f32 and `strtod_l` for f64
with an owned C numeric locale. These are established Apple libc interfaces;
see [Apple's manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/strtod_l.3.html).
It parses f32 directly, avoiding double rounding through a double intermediate.

The existing decimal grammar runs first, including sign, exponent and complete
input validation. The existing error-code and bit-result logic remains shared:
syntax is code 1; nonfinite results and nonzero significands rounded to zero are
code 2. Representable subnormals remain valid even when libc sets `ERANGE`.
Signed zero is retained. The helper temporarily selects nearest rounding and
restores the thread's rounding mode, exception environment and errno. It does
not change the process locale. Integer parsing and Linux/Windows production
`from_chars` paths remain unchanged.

Regression coverage includes:

- 5,128 generated f32/f64 decimal inputs compared with the existing Linux
  `std::from_chars` result/range classification; successful values checked by
  exact bits under all four standard rounding modes.
- Golden boundaries on every Unix host, including halfway ties, a direct-f32
  double-rounding trap, signed zero, subnormal minima, normal minima, maxima,
  overflow and zero underflow.
- A comma-decimal thread locale where available, plus exact preservation of
  rounding mode, exception flags and errno. Local Linux exercised this locale;
  an unavailable locale is explicitly reported by the test.
- Actual `vd_convert_parse` ABI calls for malformed grammar, embedded NUL,
  infinity/NaN/hex rejection, syntax-before-range precedence, range codes,
  zero with a huge exponent, signed-zero bits and subnormal bits.

A disposable copy of `conversion.cpp` selects just the Apple parsing branch on
Linux and links it ahead of the normal runtime archive for those same ABI tests.
All other platform headers/runtime code remain Linux. This is a libc integration
simulation, **not Apple libc or macOS 14 native acceptance**. The simulation
script is retained with the compact evidence.
