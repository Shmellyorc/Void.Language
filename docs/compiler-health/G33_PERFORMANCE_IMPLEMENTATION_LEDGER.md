### G46 applicability of established solutions

- LLVM BOLT uses a runtime profile to reorder a linked binary. The pinned ELF LLD also provides call-graph section sorting. These are established deployment tools and their applicability to the measured Linux executable does not establish a source fix or native Windows parity. The merged LLD balanced partitioning reland targets startup page faults and compressed size. Its objective gives no basis for selecting a placement for the already-hot integer loop. [BOLT workflow](https://llvm.googlesource.com/llvm-project/+/refs/heads/main/bolt/docs/OptimizingClang.md) · [Pinned LLD call-graph sorter](https://github.com/llvm/llvm-project/blob/7a941dfb2877a0b8cf30323fefa85ad019e0b0f5/lld/ELF/CallGraphSort.cpp) · [Merged LLD #125559](https://github.com/llvm/llvm-project/pull/125559).
- Source-level cold outlining already applies to the GC poll. `Runtime::poll` in `src/runtime/abi.cpp` leaves the managed-context and request checks on the fast path and outlines the lock and rendezvous. The worker checkpoint in `src/runtime/async.cpp` already has a no-worker return. The G46 isolated coordination object introduces no extra work in either measured integer call path. An additional outline or translation-unit shuffle has no demonstrated benefit apart from incidental placement. [Clang `cold` attribute](https://clang.llvm.org/docs/AttributeReference.html#cold) · [G46-F matched linked images](G46F_UTF8_DECODE_REGRESSION_CORRECTION.md#exact-relinks-and-source-attribution).
- OpenJDK C2's merged loop strip mining preserves a periodic safepoint outside the inner chunk. Go's asynchronous preemption uses its own safe-point and register/root rules. Transferring either approach would change VOID's existing GC or worker observation boundaries and requires an independent contract proof. The unchanged linked hot-path work gives no evidence that a G46 check can be removed. [OpenJDK 8186027](https://github.com/openjdk/jdk/commit/386e258e20eb) · [Go preemption implementation](https://go.googlesource.com/go/+/refs/heads/master/src/runtime/preempt.go).

No bounded G46 source correction was established. This review produced no new benchmark or qualification results. The original exact Linux and Windows receipts and the rejected malformed-input/OOM prototype remain with the preserved candidate.

### G45 LLVM experiment remains on HOLD

- The open MachineSinking draft #239536, head `bdc65bd5f4073622d6207bf8b58df84a3d6e9581`, independently identifies the same layout-order repeated-sweep mechanism as G45-U. Its unconditional RPO over reachable blocks matches the original G45 solution in intent. The G45-U delayed variant kept the first two layout-order sweeps to avoid changing the ordinary case. The draft also caches physical-register queries, use-dominance and successor/pressure data, and adds a direct dominator-chain jump. Its posted Reactant timings combine those changes. The draft's cross-target checks include an AMDGPU MachineSinking crash and a RISCV failure. The `MachineSink.cpp` hunk set failed `git apply --check` against the byte-verified 23.1.4 source at `7a941dfb2877a0b8cf30323fefa85ad019e0b0f5`. [Open draft #239536](https://github.com/llvm/llvm-project/pull/239536) · [Draft test results](https://github.com/llvm/llvm-project/pull/239536#issuecomment-6684064379) · [G45-U sweep proof](G45U_MACHINESINKING_PROOF.md#independent-reproduction-and-invariant).
- LLVM previously shipped a fix for expensive physical-register scans in the critical-edge heuristic and bounded optional loop sinking. The later opt-in cycle sinking extension targets register pressure. These changes address different work from the normal repeated full-function sweeps. The newer merged kill-flag removals target real repeated work but follow mainline's November verifier change prohibiting virtual-register kills. The pinned verifier still checks virtual-register kill annotations against live-variable analysis.
