## Windows file-symlink incident

Windows 10 Home x64, NT build `10.0.19045.6466`, Debug and Release in the G12 local qualification. The two controls supply distinct observations.

- **`io_execution` failed in both profiles.** The unchanged source fixture ran through `voidc run <generated-main.void> --no-opt`. At check 91 it expected the file symlink from `io.create_symlink(link_target, "link.txt")` to succeed. The process exited **91**, stdout was `check 91 failed` followed by LF, and stderr was empty. This fixture emitted no Windows native error number. [Fixture and process assertions](../../tests/io/execution.py)
- **`io_atomic_save_native` passed in both profiles.** The native C++ fixture called `std::filesystem::create_symlink` and directly observed **1314 (`ERROR_PRIVILEGE_NOT_HELD`)**. The existing fallback verified atomic save refused an NTFS junction. Directory synchronization reported `completed=1 code=0`. [Native control](../../tests/io/atomic_save.cpp)
- **Both G12 archive tests passed in Windows Debug and Release.** The archive outcomes and the unrelated `io_execution` failure retain separate test results. [G12 native results](../archive/ZIP_EXPORT.md#native-results)

Together these observations strongly support a missing Windows file-symlink privilege as the common environmental limitation. Error 1314 came from the native control. No UAC prompt was observed, and there is no evidence of a separate UAC defect. Future qualification needs an unchanged `io_execution` replay in a Boss-authorized Windows session already able to create a file symlink, with Debug and Release outcomes and the actual process status preserved. No privilege bypass or change to check 91 is part of this audit. The historical G06 record also lists the async source suite at check 91.
