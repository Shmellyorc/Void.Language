# LLVM 19 → 23 compatibility and optimization audit 

22 November 2026. Read-only review against `c6015735` (backend inherited from accepted `9959ab72`). Source line numbers below refer to `git show HEAD:<path>`, before the focused corrections. No builds, experiments, production edits or Git mutations were performed for this inventory. Historical measurements are explicitly attributed; they are not fresh measurements.

This is deliverable A. See [focused corrections and qualification](RUNTIME_ABI_CORRECTIONS.md) for deliverable B. No optimization restriction or guard is removed by this work.

## Conclusion

No reviewed production guard is demonstrated obsolete merely because VOID upgraded LLVM. Two particularly important assumptions are disproved:

- **SLP=false was not established as an LLVM 19 defect workaround.** Both pinned LLVM 19.1.7 and 23.1.4 initialize `PipelineTuningOptions::SLPVectorization=false`. VOID originally inherited that default; `175c08c8` made it explicit while adding AOT TargetMachine analysis. Existing experiments kept SLP off, so they do not establish either SLP correctness or profitability for VOID.
- **Scalar-default elimination is not an old LLVM19 workaround.** It entered in LLVM23-era G44 (`894e2e8d`, 15 November), backed by matched final-code and compile-time evidence. LLVM23 eventually removes these stores itself, but pays substantial promotion/SSA construction cost first. Equivalent final output is not equivalent compilation cost.

Keep existing safety obligations and accepted target/optimizer scope. A new SLP trial is conceivable but not authorized implementation; no speedup can be claimed. The investigated ABI/meta defects are separate from permission to change optimization policy.

## Obsolete mechanisms already removed, not new deletion opportunities

`a4ca3e58` removed the **LLVM19/libc++19 `_LIBCPP_ENABLE_EXPERIMENTAL` stop-token opt-in** and its exact190107 fallback, retaining real cancellation probes. The current Apple probe was strengthened to execute and uses vendor headers matched to the system library. Migration replaced removed `CreateGlobalStringPtr` with `CreateGlobalString`, older intrinsic lookup with `getOrInsertDeclaration`, and string target APIs with typed `Triple`; MC iterator/subtarget API fixes are recorded in `docs/llvm23/IMPLEMENTATION.md`. There is no current production LLVM19-version branch in the scanned `src/`, `cmake/`, or root CMake source. Historical files and notices are not active code paths.

The root CMake comment that official Linux SDK archives *can* contain bitcode is historical context, not proof this23.1.4 SDK still incurs repeated19-era LTO. Current migration evidence identified native objects. Retaining the pinned linker does not itself cause an extra LTO pass; do not remove linker checks based on that comment.

## Bounded next experiments only if separately approved

1. **SLP isolation**: existing accepted AOT pipeline, flip only SLP, preserve strictFP and generic CPU. Independent scalar groups plus branch/alias/failure/managed controls; inspect IR/instructions, cold compile+first-run and warm execution. Expected benefit unquantified; scope/code-size/register-pressure/startup risks real. Reject changes that save kernel time but materially harm ordinary cold execution.
2. **Repeated typed-IR validation attribution**: compare exact module identity and facts across admission/lowering; retain revalidation after actual rewrites. Reuse G44 observations. Only pursue if exclusive validation cost is consequential; do not substitute LLVM verification for VOID proofs.
3. **No other removed guard or pass-policy change is justified by this inventory.** Existing historical tests do not prove current native acceptance for a changed ABI; accompanying focused oracle/native tests are separate.
