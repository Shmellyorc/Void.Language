# Slice 7 G4-W2 Windows image selection

**Decision for review.** Keep production Windows G4 on hold. The protected-file and import-free controls passed within the boundaries described below. The supported unpackaged loader interface does not bind a validated file handle and SHA-256 to executable DLL selection. A controlled process narrows the state that needs proof. This checkpoint did not establish that the launcher can hold all of that state fixed through executable selection. The smallest next checkpoint is a managed Windows 10 x64 App Control for Business experiment, if Boss and Golden Wrench accept a device-level policy prerequisite. The accepted Linux G4-L profile is outside that deployment decision. A protected deployment would need a trusted installer and launch identity, a protected executable and manifest, an immutable plan and staged DLL root, controlled current directory, environment and inherited handles, and a known startup import closure before the launcher's first instruction. The OS owns DLL selection, system forwarding, activation, compatibility policy, KnownDLLs, API-set hosts and OS-mediated loads. An untrusted project, installer input, file writer, user manifest or package must have no native-binding authority. The proposed threat model assumes a trusted OS and administrator and no already-executing untrusted native code in the trusted process. An unrestricted actor that can write the launch root, inject into the process or control machine policy is outside the demonstrated scratch protection. A scan for a loaded name and an activation key at one instant cannot reserve either. An architecture that trusts a closed startup and loader state must establish how the closure is created and maintained using supported contracts.

## Alternatives and recommendation

| Candidate | Pre-initializer authority | JIT, installed AOT, ABI and deployment |
| --- | --- | --- |
| **A. Protected launcher, import-free DLLs and an explicit table** | The launcher can reduce inputs, hold local files, check the active context and reject known invalid PE features. It must independently establish that the executable loader selects the same admitted object. The supported path interface and current startup/namespace evidence leave that step open. | A local in-process table preserves normal and O2 JIT call shape and native x64 ABI, with no IPC overhead. Relocated AOT requires an independently trusted installed launcher/root and no bundled provider import before admission. The synthetic profile is simple to exercise, while a conventional raylib DLL has a broader dependency surface. |
| **B. Enforced OS image allowlist plus protected launcher and Runtime admission** | UMCI can stop an image disallowed by effective policy before attach. A policy that allows a different candidate cannot distinguish which file the Runtime intended. Bound the effective policy and loader inputs, reject competing same-name allowed images and retain flat-digest artifact approval. | Native G2/G3 calls can remain in process. Measure normal/O2 JIT under the actual policy, including any dynamic-code policy interactions. AOT must run from a relocated protected install and pass policy with the exact authorized artifacts. This has the most credible route to approving raylib, CRT and graphics code under explicitly separated trust scopes. It adds endpoint policy ownership, signing or hash management, installation and update/rollback requirements. |
| **C. Fresh helper process** | A small helper has fewer preexisting modules and isolates crashes. Startup and executable DLL selection still use Windows loader policy. For A or B, keep compiler and Runtime responsibilities separated. Before eager VOID globals, trusted host admission would verify the immutable plan, descriptors, target ABI and exact PE artifacts. Start with import-free application provider images. Reject unreviewed imports, delay imports, entry points, TLS, load metadata and forwarded exports. The Windows x64 target-compiled thunks retain the independently validated typed-IR signatures. Once image authority has been established, confirm the map and each direct export owner before publishing a complete, immutable, Runtime-owned binding table. Keep G2 bounds and output commits at the call boundary. Pin the acquisition generation and its loaded release thunk through G3's terminal native return. Providers keep the trusted fresh-ownership assumption. Compatible reload must preserve old table and module leases for outstanding resources, and shutdown must release them before retirement. AOT must recreate the admission before user code, from its installed root independent of source, working directory and ambient search paths. Neither project inputs nor provider thunks may add native authority or mutate a process-global table. W1 exercised an explicit caller-owned table with a C record, a span and an opaque token. Production integration, JIT and AOT remain unqualified for Windows G4. For C, a protected child must attest a specific launch generation and finish admission before accepting requests. A synchronous call incurs at least one request and one response, with bounded G2 input bytes copied into child-owned storage and returned output staged in the parent until success. Records need a versioned representation and validation before the child constructs local ABI values. G3 wrappers must use generation-scoped remote resource IDs. Only the helper owns raw pointers. The helper must serialize closes against live borrows and release on the correct owner thread. If it crashes, the parent invalidates the generation and stops admitting calls on old IDs. An interrupted release is indeterminate and cannot be retried against a restarted generation. Graceful shutdown must drain calls and callbacks before terminal releases and module retirement. A main-thread event loop can dispatch window and rendering commands and deliver bounded callback events. Synchronous callbacks with return values, reentrancy and owner-thread handoffs need separate design. A frame composed of many small calls multiplies round trips. A general batched transport could reduce them, with costs and semantics to be measured separately. No IPC or performance benchmark was implemented here.

## Dynamic raylib feasibility

The raylib 5.5 source was reviewed as a concrete example, with no dependency pin or binary chosen. Its shared Windows desktop GLFW build links OpenGL, GDI and WinMM. The exact PE closure depends on compiler, CRT linkage and enabled backends. MSVC `/MD` uses the DLL runtime and `/MT` links the runtime into the image. Ordinary DLL startup can invoke CRT initialization even without a provider-written `DllMain`. The future admission needs the actual PE entry, TLS, static imports, delay imports and forwarded exports of the exact deliverable. Choosing a static CRT cannot by itself establish a no-entry or no-import image. [raylib shared build](https://github.com/raysan5/raylib/blob/5.5/src/Makefile) · [MSVC runtime options](https://learn.microsoft.com/en-us/cpp/build/reference/md-mt-ld-use-run-time-library) · [Microsoft DLL/CRT initialization](https://learn.microsoft.com/en-us/cpp/build/run-time-library-behavior).

The bundled GLFW Win32 path loads system components such as User32, DirectInput, XInput and DWM as needed. OpenGL can select an installed driver ICD through Windows. That runtime closure must be covered by the explicitly trusted OS and driver policy for each supported deployment, with any application-bundled CRT or graphics DLL separately admitted. The backend uses GLFW callbacks and polls or waits for input. Window creation, event processing and destruction use the owning main thread under GLFW's contract. Current OpenGL contexts and error callback routing carry their own thread requirements. Ordinary dynamic raylib therefore needs more than the synthetic import-free profile.
